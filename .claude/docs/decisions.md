# Рішення та відкриті питання

## Прийняті рішення (з аналізу ТЗ)
- **Пакетний менеджер = npm (workspaces)**, не pnpm — рішення замовника (відхилення від §2/§62). Один `package-lock.json` у корені, у CI `npm ci`.
- **ORM = Prisma.** §62 каже «Prisma або Drizzle», але §33 однозначно фіксує Prisma. Діє §33.
- **CI/CD = GitHub Actions + AWS** (§53 уточнює «або аналог» з §62).
- **Роут новин = `/blog`**, у меню називається «Новини»; Article має поле `type` (PROMO/NEWS/ARTICLE/VIDEO + експертні типи).
- **Локально S3 = MinIO, email = Mailpit** (додатково до Postgres/Redis/Meilisearch з §52), щоб не залежати від AWS у dev.
- Розділ §66 у ТЗ відсутній (нумерація 65 → 67) — нічого не втрачено.
- **TypeScript ~6.0**, не 7.x: typescript-eslint підтримує лише `<6.1`. Оновити, коли typescript-eslint додасть підтримку TS 7.
- **ESLint 9** (flat config), не 10: не всі плагіни в eslint-config-next готові до 10.
- **Спільні пакети** (`types`, `validation`, `config`, `api-client`) збираються **tsdown** у ESM + CJS (`.mjs`/`.cjs`), бо NestJS працює в CommonJS. tsup відкинуто: його DTS-збірка ламається на TS 6 (`baseUrl`). `packages/ui` — без збірки, Next споживає TS-джерело через `transpilePackages`.
- Імена workspace-пакетів: `@ml/*`. Порти: web 3000, api 4000.
- **Env: один `.env` у корені monorepo** (шаблон `.env.example`), його читають docker compose, api і web. `@ml/config` (zod) шукає `.env` вгору від cwd; змінні процесу мають пріоритет над файлом; невалідний env → падіння при старті (імена змінних у помилці, без значень). Web валідує env лише у фазах dev/build/start.
- **Тестова БД `ml_test`** створюється init-скриптом Postgres (`infrastructure/docker/postgres/init`) — лише при першій ініціалізації volume (`npm run infra:reset`, щоб перестворити).
- **Образ MinIO = `pgsty/minio`** (community-збірка, версія закріплена в compose): офіційні `minio/minio`/`minio/mc` більше не публікуються. Той самий образ містить `mc` і створює бакети (`minio-init`, profile `init`, запускає `npm run infra:up`). Код працює з S3 API, тож образ можна замінити без змін у застосунку.
- **Prisma 7** (стабільна 7.10; `latest` у npm = 8.0 RC — не беремо). Схема й міграції в `apps/api/prisma`, конфіг `apps/api/prisma.config.ts` (сам читає кореневий `.env`). Генератор `prisma-client` (CJS) → `apps/api/src/generated/prisma` (у .gitignore), підключення через driver adapter `@prisma/adapter-pg`. `migrate dev` клієнт не генерує → Turbo-задача `db:generate` є залежністю dev/build/lint/typecheck/test. Env у Nest — через `@Inject(API_ENV)` з глобального `ConfigModule`. Команди: `npm run db:migrate | db:deploy | db:reset | db:studio`.
- **API-маршрути й OpenAPI**: глобальний префікс `/api` + URI-версіонування (default `v1`) → `/api/v1/...`. Swagger UI `/api/docs`, JSON `/api/docs-json` — реєструються лише при `NODE_ENV !== production` (у prod маршрутів немає, 404). Nest CLI-плагін `@nestjs/swagger` (`*.dto.ts`, `*.controller.ts`, `introspectComments`) сам описує DTO з TS-типів і JSDoc; operationId = `<Controller>_<method>` (стабільні імена для api-client, крок 4.7). `createOpenApiDocument()` у `src/openapi/swagger.ts` — єдине джерело документа.
- **Логування = `nestjs-pino`** (`src/logging`). Кожен рядок логу в межах запиту має `requestId` (AsyncLocalStorage + `quietReqLogger`), включно з `new Logger()` у сервісах. `requestId` береться з вхідного `X-Request-Id`, якщо він валідний (`[A-Za-z0-9._:-]{8,128}`), інакше — UUID; завжди повертається в заголовку відповіді `X-Request-Id`. Dev — `pino-pretty` в один рядок; інакше — JSON (`level` словом, `time` ISO). Тіла запитів не логуються; `authorization`, `cookie`, `set-cookie`, `*.password/token/totp/secret` → `[REDACTED]`. Swagger-запити не логуються.
- **Валідація = class-validator + class-transformer** (не nestjs-zod: той не підтримує NestJS 12). Глобальний `ValidationPipe` (`whitelist` + `forbidNonWhitelisted` — зайві поля → 400, `transform`). Плагін Swagger переносить обмеження декораторів в OpenAPI. Zod з `@ml/validation` — для форм на фронті.
- **Єдиний формат помилок** (`src/common/errors`): кожна не-2xx відповідь = `{ statusCode, code, message, requestId, details? }`; `code` — машинний (`ErrorCode`), клієнт розгалужується по ньому, не по `message`; `details` = `[{ field: "items.0.qty", messages }]`. Доменні помилки — `throw new AppException(ErrorCode.X, msg, status)`. Prisma P2002 → 409, P2025 → 404. Будь-яка 5xx/невідома помилка → «Internal server error» без деталей; причина й стек ідуть у лог через `res.err` (один рядок з `requestId`). Pipe і filter реєструються через `APP_PIPE`/`APP_FILTER` в `ErrorsModule` (працюють і в e2e-тестах). У Swagger кожна операція має `default`-відповідь `ErrorResponseDto`.
- **Health (§50)**: `GET /health` (liveness, без перевірок залежностей) і `GET /health/ready` (PostgreSQL `SELECT 1`, Redis `PING`, Meilisearch `/health`; паралельно, таймаут 2 с кожна) — поза `/api` і без версії. Ready → 200 `{status:"ok",checks}` або **503** з тим самим тілом (навмисно не єдиний формат помилок, щоб було видно, що саме впало); публічно лише `timeout`/`unreachable`, деталі — у лог. Tria в readiness не входить (її недоступність не має знімати трафік). Власна реалізація замість `@nestjs/terminus` (конфлікт 503-відповіді з фільтром помилок). Health-запити не логуються. Налаштування маршрутів — `configureApp()` у `src/app.setup.ts` (спільне для main і e2e).
- **Redis-клієнт** = ioredis 6 (BullMQ 6 приймає його як peer), `RedisModule` → `@Inject(REDIS)`. `enableOfflineQueue: false` + `maxRetriesPerRequest: 1`: при недоступному Redis команди падають одразу, а не висять — код, що кешує, має деградувати без Redis (§34).
- **Jobs = BullMQ 6 + `@nestjs/bullmq`** (`src/jobs`). Усі черги §29 + `system` + `dead-letter` зареєстровані глобально (`QueueName`, префікс ключів `ml`), інжект — `@InjectQueue(QueueName.X)`. Дефолти: 3 спроби, exponential backoff 1 с, completed зберігаються 24 год, failed — 7 днів. Кожен процесор наслідує `BaseProcessor` і реалізує `handle(job, signal)`: логи з `jobId/queue/job/attempt` (`PinoLogger.runInContext`), timeout `timeoutMs` (5 хв, AbortSignal для кооперативної зупинки), після останньої спроби або `UnrecoverableError` → копія в `dead-letter` (id `<queue>__<jobId>`). Ідемпотентність — детермінований `jobId` (без `:` — BullMQ забороняє). Поки що workers працюють у процесі API; винесення в `apps/worker` — при масштабуванні (17.4). Bull Board — `/api/queues`, лише dev, без auth; у production моніторинг через `/admin` з RBAC (11.3).
- **API-клієнт = `@hey-api/openapi-ts`** (SDK-функції + типи + fetch-клієнт), не openapi-typescript (той підтримує лише TS 5). Ланцюжок `npm run api:generate`: `apps/api` збирається в `dist-openapi` (окремо від `dist`, щоб не ламати dev-watch; Swagger-плагін діє лише при `nest build`) → Nest у **preview-режимі** (без БД/Redis) пише `packages/api-client/openapi.json` → hey-api генерує `src/generated`. І `openapi.json`, і згенерований код **комітяться** (контракт видно в diff); CI перегенеровує й падає, якщо є різниця. Використання: `createApiClient({ baseUrl })` і `appGetRoot({ client })` — без глобального клієнта. У web серверний клієнт — `apps/web/src/lib/api.ts`. Сторінки, що ходять в API, — `dynamic` (API недоступний під час build).
- **Тести = Vitest 5 + `unplugin-swc`** (esbuild не зберігає метадані декораторів, потрібні для DI Nest). Проєкти: `unit` — `src/**/*.spec.ts`, без інфраструктури (`npm run test:unit -w @ml/api`); `integration` — `test/**/*.int-spec.ts`, повний `AppModule` на реальних PostgreSQL `ml_test` і Redis db 1 (`DATABASE_URL_TEST`, `REDIS_URL_TEST`), файли послідовно. `globalSetup` відмовляється стартувати, якщо тестові URL не задані або збігаються з dev (назва БД має закінчуватися на `_test`), робить `prisma migrate deploy` і `FLUSHDB`. Хелпери: `createTestApp()` (та сама маршрутизація через `configureApp`), `resetDatabase()` (TRUNCATE усіх таблиць, крім історії міграцій). `npm test` запускає обидва набори → потрібен `npm run infra:up`; у CI — service-контейнери Postgres/Redis/Meilisearch. Swagger-плагін у тестах не діє (схеми DTO в тестах не перевіряти). Конфіг — `vitest.config.mts` (ESM у CJS-пакеті).
- **Модель каталогу: локалі й дерево (5.1).** Мови — таблиця `locales` (uk default, ru, en; вставлені міграцією), не enum: нова мова = новий рядок (§59). Переклади — `<entity>_translations` з PK (entityId, locale) і FK на `locales`. **Slug один на всі мови** в основній таблиці (як у прикладі §59); якщо рішення 1.4 вимагатиме slug на мову — окрема міграція. **Категорії:** `parentId` + матеріалізований `path` (slug-и через `/`, глобально унікальний) + `depth`; slug унікальний лише серед сусідів (у дереві повторюються «Інше», «Чохли»). Видалення категорії з дітьми заборонене (Restrict), переклади видаляються каскадом. Перенесення категорії → сервіс перераховує `path/depth` піддерева (крок 10.4). **Бренди:** `name` не перекладається (власна назва), `description` — у `brand_translations` (SEO — лише в `seo_metadata`, див. 5.5); `country` — ISO 3166-1 alpha-2. ID — UUID v7. Зображення категорій і логотипи брендів — FK на Media у 5.4 (файли лише в S3). У тестах `resetDatabase()` не чіпає `locales` і `_prisma_migrations`.
- **Товари й варіанти (5.2).** `status` (enum DRAFT/ACTIVE/ARCHIVED) — життєвий цикл в адмінці; видимість на сайті — `isPublished` + `publishedAt` (обидва поля з §6). `isSale`/`isAntidron` — булеві прапорці товару з індексами `(is_published, is_sale|is_antidron)`. Товар ↔ категорії — `product_categories` (PK product+category, `position` для ручного сортування); **основна категорія — `products.primary_category_id`** (одна за визначенням; canonical/breadcrumbs, питання 9), сервіс гарантує, що вона є й у `product_categories`. У кожного товару ≥ 1 варіант (простий товар = 1 варіант); ціни/залишки — лише на варіантах (5.4). SKU товару й SKU варіанта унікальні кожен у своїй таблиці. Вага/розміри — `weight_g`, `length_mm`, `width_mm`, `height_mm` (Int), не JSON. Назва/опис товару — `product_translations`. Видалення товару каскадно видаляє варіанти, переклади й зв'язки; бренд/категорію з товарами видалити не можна (Restrict). Режим продажу зброї (питання 1.1) — не додано, до етапу 12.
- **Атрибути (5.3).** `attributes` (`code` — стабільний ключ для фільтрів/імпорту, `type` enum STRING/NUMBER/BOOLEAN/SELECT/MULTI_SELECT/RANGE, `is_filterable`, `is_searchable`, `is_variant_option`), назва й **одиниця виміру** — у `attribute_translations`. Опції SELECT — `attribute_values` (`code` унікальний у межах атрибута, для URL фільтрів) + `attribute_value_translations.label`. **Людський текст — лише як SELECT-опція з перекладами**; STRING — мовно-нейтральний (номер моделі, стандарт). `product_attribute_values`: окрема колонка на тип (`value_id`, `value_number` Decimal(14,4), `value_number_to` для RANGE, `value_boolean`, `value_text`); MULTI_SELECT = рядок на опцію; `variant_id = null` → значення всього товару, інакше — варіанта. CHECK у БД: рівно одна колонка значення; `value_number_to ≥ value_number` (окрема SQL-міграція — Prisma не описує CHECK, drift не виникає). Відповідність типу й унікальність (товар, варіант, атрибут) перевіряє сервіс. Provenance (§67.10): `source` (MANUAL/TRIA/SUPPLIER_FEED/IMPORT), `source_external_id`, `source_updated_at`, `verified_at`. `category_attributes` (position, is_required, is_filterable); підкатегорії успадковують атрибути предків (сервіс, по `path`). Атрибут/опцію, що використовуються, видалити не можна (Restrict).
- **Склад, ціни, медіа (5.4).** `warehouses` (`code` унікальний, `external_id`). `inventory` — PK (variant, warehouse), `quantity`/`reserved` ≥ 0 (CHECK), **`available` — STORED generated column `quantity - reserved`** (у Prisma `@default(dbgenerated(...))`, SQL виправлено вручну; ніколи не писати в нього; може бути < 0, коли Tria зменшила залишок нижче резерву — InventoryService рахує як 0). Типи цін — таблиця `price_types` (`retail` default вставлено міграцією; wholesale/dealer/VIP — нові рядки). `prices`: variant × price type × currency (ISO 4217, default `UAH`) × період (`valid_from/valid_to`, null = відкритий); `price`, `old_price` (перекреслена), `sale_price` (≤ price) — Decimal(12,2), CHECK на невідʼємність і порядок дат; ефективна ціна = `sale_price ?? price`, серед перекриттів — найпізніший `valid_from` (PricingService, 6.4). `media` зберігає **S3-ключ, не URL** (URL = `S3_PUBLIC_URL`/CloudFront + key), `filename`, `mime_type`, розміри, `size_bytes`; `alt`/`title` — `media_translations`; AVIF/WebP-рендишени — черга `images` (10.5). `product_media`: PK (product, media), `position`, `is_primary` (частковий унікальний індекс — максимум одне головне фото), опційний `variant_id` (фото конкретного варіанта). `categories.image_id`, `brands.logo_id` → media (SetNull); медіа, що використовується в галереї, видалити не можна.
- **SEO, редиректи, інтеграції (5.5).** **Єдине джерело SEO — `seo_metadata`** (entity_type PRODUCT/CATEGORY/BRAND/PAGE/ARTICLE/ROUTE × entity_id × locale; title, description, canonical, noindex/nofollow, og_title/og_description/og_image_id). Колонки `seo_title/seo_description` у `category_translations`/`brand_translations` і `categories.canonical` з 5.1 видалено: SEO не повинно жити у двох місцях (§67.10); порожні поля → шаблон. Поліморфний звʼязок без FK: сервіс-власник видаляє SEO разом із сутністю; ROUTE = статичний шлях (`/sale`). `redirects`: `from_path` унікальний (нормалізований шлях), 301/302 з `to_path`, **410 Gone без `to_path`** (знятий товар, §14.2), CHECK на коди/ціль/самопосилання; `source` MANUAL/SLUG_CHANGE/IMPORT, лічильник `hits`; ланцюжки й петлі відсікає сервіс. `integration_mappings`: унікальні (integration, entity_type, external_id) → `internal_id`, `payload_hash` останнього застосованого payload (пропуск незмінених, ідемпотентність §30). `sync_logs`: integration, scope (products/prices/inventory/orders), trigger (SCHEDULED/MANUAL/RETRY), status (RUNNING/SUCCESS/PARTIAL/FAILED), `job_id`, лічильники created/updated/skipped/failed, `errors` — обмежена вибірка JSON (повні деталі — у логах за jobId).
- **Seed (5.6).** `apps/api/prisma/seed/index.ts` (через `tsx`, Prisma `migrations.seed`), **ідемпотентний** (upsert за природними ключами: `path`, `code`). Дані — TS-файли в `prisma/seed/data/`: дерево категорій згенероване один раз з `categories.md` (136 категорій, 3 корені; назви лише uk — ru/en fallback на uk до перекладу в адмінці), 13 базових атрибутів з перекладами uk/ru/en і привʼязкою до категорій, 2 dev-склади (реальні прийдуть із Tria). Slug — `slugify()` у `src/common/text/slugify.ts`: офіційна транслітерація КМУ № 55 (2010), `зг→zgh`, Y-форми на початку слова; використовувати всюди (адмінка, імпорт). Unit-тест цілісності seed-даних (унікальні шляхи, існуючі категорії атрибутів). Команди: `npm run db:seed`, `npm run db:reset` (= `migrate reset --force` + seed; **Prisma блокує reset від AI-агента без явної згоди користувача** — питати щоразу, лише dev-БД).
- **Фейкові дані й ERD (5.7).** `prisma/seed/fake.ts` (`npm run db:seed:fake`, входить у `db:reset`): 50k товарів, 500 брендів, ~52k варіантів/цін, ~104k рядків залишків, ~50k значень атрибутів; **детерміновано** (faker seed 42) — заміри порівнювані; розмір — `FAKE_PRODUCTS`. Відмовляє в production, пропускає, якщо товари вже є. UUID v7 генеруються на клієнті, вставка `createMany` пакетами по 2 000 рядків, порціями по 5 000 товарів; наприкінці `ANALYZE`. Результат: `db:reset` (міграції + seed + 50k) ≈ **87 с** (ціль < 3 хв), БД ≈ 119 МБ. Назви товарів лише uk. ERD — `npm run db:erd` → `docs/database/erd.md` (Mermaid з `information_schema` живої БД: групи доменів + карта звʼязків); нова таблиця без групи в `prisma/erd.ts` → скрипт падає. Перегенеровувати після кожної міграції.
- **Catalog API: категорії, кеш, локалі (6.1).** `GET /api/v1/categories` — дерево активних категорій (`{ locale, items }`); `GET /api/v1/categories/by-path?path=a/b` — сторінка категорії з `breadcrumbs` (корінь → поточна) і прямими дочірніми; шлях — query-параметр (OpenAPI не описує `/` у path-параметрі). Неактивна категорія ховає все піддерево (404). **Локаль** (`src/i18n`): `?locale=` → `Accept-Language` → default з таблиці `locales`; непідтримувана мова — не помилка, а fallback; некоректний формат → 400. Публічні query-DTO наслідують `LocaleQueryDto`; відповідь має заголовок `Content-Language`. Переклади — fallback на uk **по кожному полю**; без назви — slug. Список локалей кешується в памʼяті процесу на 60 с. **Кеш** (`src/cache`, `CacheService.getOrSet/del`): JSON у Redis під префіксом `ml:cache:`; будь-яка помилка Redis → дані з БД без кешу (§34). Категорії кешуються **одним значенням на локаль** (`categories:{locale}`, усе видиме дерево з описами, TTL 1 год як страховка); дерево/breadcrumbs будуються з нього в памʼяті. Інвалідація — `CategoriesService.invalidateCache()` (видаляє ключі всіх локалей); викликати з адмінки (10.x), імпорту й Tria-sync після змін категорій, перекладів або зображень. URL медіа = `S3_PUBLIC_URL` + key (`src/media/media-url.ts`).
- **Catalog API: товари, ціни, наявність (6.2 + 6.4).** `GET /api/v1/products` — опубліковані товари (видимість = `isPublished`), найновіші першими (`publishedAt desc, id`), пагінація `page`/`limit` (≤ 100), фільтри `category` (шлях, **разом із підкатегоріями**) і `brand` (slug); невідома/прихована категорія чи неактивний бренд → 404. Це SQL-шлях: фасети й сортування за ціною — через Meilisearch (7.4), SQL лишається fallback-ом, коли Meilisearch недоступний. `GET /api/v1/products/{slug}` — картка: переклади з fallback по полю, бренд (лише активний), основна категорія + breadcrumbs (з кешу категорій; прихована → `null`), галерея (головне фото першим; alt → назва товару), характеристики товару (`variantId = null`) і опції варіантів (значення варіанта), активні варіанти з ціною й наявністю по складах. **Гроші в API — рядок з 2 знаками (`"1299.00"`), не float.** **PricingService** (`src/catalog/pricing`) — єдине місце вибору ціни: прайс `is_default` (retail), валюта `UAH`, серед рядків з `[validFrom, validTo)` перемагає найпізніший `validFrom` (відкритий = найстаріший), далі найновіший `createdAt`; продажна = `salePrice ?? price`, перекреслена = `oldPrice` або `price` при `salePrice`, показується лише якщо більша; ціна товару = мінімум по варіантах + `hasPriceRange`. **InventoryService** (`src/catalog/inventory`) — `available` кожного рядка (варіант × склад) обрізається до 0 **до** сумування, неактивні склади виключені; `StockSnapshot.of(variant)` / `.total(variants)`. Checkout (12.3) і індексація (7.x) мають використовувати ці ж сервіси. Спільний хелпер перекладів — `translator()` у `src/i18n/translate.ts`. Заміри на 50k: картка 10–25 мс, списки 20–45 мс (навіть сторінка 2000) — кеш карток не потрібен.
- **Catalog API: бренди й вітрини (6.3 + 6.5).** `GET /api/v1/brands` — активні бренди, що мають ≥ 1 опублікований товар, за назвою (`localeCompare` uk), з `productCount` і логотипом; назва бренду не перекладається, тому **один кешований знімок `brands:list` на всі мови** (TTL 10 хв, бо публікація товарів ключ не інвалідує; записи брендів мають викликати `BrandsService.invalidateCache()`). Лічильники — один `GROUP BY brand_id` (~10 мс на 50k) замість підзапиту на бренд (~250 мс). `GET /api/v1/brands/{slug}` — будь-який активний бренд (також без товарів — SEO-сторінка існує), `description` з fallback по полю, `seo` {title, description, noindex} з `seo_metadata` (BRAND × brand.id), порожнє → шаблон на storefront; товари бренду — `GET /products?brand=`. **Вітрини `/sale` і `/antidron` — не окремі endpoints, а фільтри `sale=true` / `antidron=true` у `GET /products`** (комбінуються з category/brand; приймаються лише `true`/`false`). Локалізація (6.5) тепер застосована до всіх публічних endpoints каталогу.
- **Пошук: схема індексу (7.1).** `src/search` (`SearchModule`), клієнт `meilisearch` 0.62 (ESM-only, вантажиться з CJS через require(esm) Node 24), токен `MEILI`; ключ лише на сервері, storefront у Meilisearch не ходить. **Індекс на кожну активну локаль** `<MEILI_INDEX_PREFIX>_products_<locale>` (prefix `ml`, у тестах `ml_test`), primary key `id`, `localizedAttributes` uk→ukr/ru→rus/en→eng. Індексуються лише опубліковані товари. **Документ = надмножина `ProductListItemDto`** (displayedAttributes = рівно плитка лістингу, 7.4 рендерить без PostgreSQL) + поля пошуку/фільтрів: `priceAmount` (число для фільтра/сортування; показ — `price`-рядок), `publishedAt` (unix s), `categories` (шляхи видимих категорій **разом із предками** → `categories = "zbroia"` = піддерево), `warehouses` (коди складів із наявністю), `attrs.<code>` (лише `is_filterable`; SELECT/MULTI → коди опцій, NUMBER/BOOLEAN/STRING → масиви, RANGE → {min,max}; об'єднання товару й активних варіантів; фасети повертають коди, підписи дає API), `attributesText` (`is_searchable` як «Назва значення од.»), `variantSkus`, `barcodes`, `categoryNames`, описи plain text. Пріоритет пошуку: title → sku → variantSkus → barcodes → brand.name → categoryNames → attributesText → описи; без typo для SKU/штрихкодів. Ranking: стандартні + `inStock:desc`, `publishedAt:desc` (порожній запит = в наявності, новіші). Sortable: `priceAmount`, `publishedAt`, `title`. `maxTotalHits` 10 000, `maxValuesPerFacet` 500, `facetSearch` вимкнено (значення — коди), `proximityPrecision: byAttribute` (швидша індексація). Документи будує `ProductDocumentsService.build(ids)` → {документи по локалях, `removedIds`} через PricingService/InventoryService і кешоване дерево категорій (`CategoriesService.localized`); чиста функція `toProductDocument`. `ProductIndexService.prepare(locale, uid?)` — створює індекс і застосовує налаштування (ідемпотентно; `uid` для тимчасового індексу повного reindex + swap у 7.2); `wait()` кидає `TaskFailedError` на failed-задачі.
- **Пошук: індексація (7.2).** Черга `search-index`, `SearchIndexProcessor` (timeout 30 хв), два job-и. **`reindex-all`** — без простою: для кожної локалі заповнюється `<uid>__next` (налаштування до документів, пакети по 500 товарів курсором за id, задачі Meilisearch лише ставляться в чергу, наприкінці кожна перевіряється — невдалий пакет валить job, живі індекси не зачеплені), потім **один атомарний `swapIndexes` усіх локалей** і видалення старих даних; видалені/зняті товари зникають самі. Запит на повний reindex, поки попередній чекає/виконується, приєднується до нього (BullMQ `deduplication`), 1 спроба. **`sync-products`** `{productIds}` (≤ 500 на job, `SearchIndexer.syncProducts()` ріже й дедуплікує) — upsert документів у всіх локалях + delete для видалених/неопублікованих; якщо живого індексу нема — не створює його без налаштувань, а ставить повний reindex. **Global concurrency черги = 1** (усі workers): sync ніколи не перемежовується з reindex, тож зміни під час перебудови застосуються після swap і не загубляться. `SearchIndexer` (producer) — єдиний вхід: `syncProducts(ids)` після змін товару/перекладів/варіантів/цін/залишків/атрибутів/медіа/публікації (адмінка 10.x, Tria 11.2, checkout-резерви 12.x), `reindexAll()` після змін дерева категорій, визначень атрибутів, локалей. На старті API (крім `test`): global concurrency, **нічний повний reindex** (job scheduler `0 3 * * *` Europe/Kyiv — страховка від пропущених подій) і автоматичний reindex, якщо індексу ще немає; збої Meilisearch/Redis лише логуються. CLI `npm run search:reindex` лише ставить job (робить його запущений API); входить у `db:reset`. Заміри: 46k опублікованих × 3 локалі ≈ **45 с**, ~270 МБ на індекс; пошук/фасети по категорії 5–8 мс. Стемінгу немає («ніж» ≠ «ножі») → синоніми, керовані з адмінки (пізніше). **Meilisearch оновлено 1.16 → 1.54.0** (compose і CI): SDK 0.62 шле поле `rename` у swap, якого 1.16 не знає. Dev-том перестворено (індекси похідні, відновлюються reindex-ом). У dev watch-перезапуски API вбивають довгий job (`stalled`) — просто запустити reindex ще раз.
- **Пошук: API (7.3).** `GET /api/v1/search` (`SearchController` → `SearchService`): `q` (порожній = перегляд), `category` (шлях, з підкатегоріями; прихована/невідома → 404), `brand` (кілька: `?brand=a&brand=b` або `a,b`), `priceMin/priceMax`, `inStock`, `sale`, `antidron`, **`attr`** (повторюваний: `code:v1,v2` — коди опцій / текст / `true`,`false`; `code:min..max` — числа, одна межа необовʼязкова; невідомі чи не-filterable коди **ігноруються**, щоб старі посилання не падали), `sort` = relevance|price_asc|price_desc|newest|title, `page`/`limit` (≤ 100, `page×limit` ≤ 10 000 → інакше 400). Групи фільтрів — AND, значення в групі — OR. NUMBER фільтрується через `TO` (одне значення масиву в межах), RANGE — перетин `[min,max]`. **Фасети диз'юнктивні**: один `multiSearch` = основний запит (сторінка + фасети невибраних груп) + по запиту `limit 0` на кожну вибрану групу без її власного фільтра (обрав бренд A — бачиш лічильники інших брендів; межі слайдерів ціни/атрибутів — без власного діапазону). Відповідь: плитки `ProductListItemDto` + `facets` {brands, price, selectedPrice, inStock/sale/antidron {count, selected}, attributes [{code, name, unit, type, values[{value,label,count,selected}] | range, selectedRange}]}; вибрані значення завжди в списку (навіть count 0), порожні фасети не повертаються; опції — у порядку атрибута. Підписи: метадані filterable-атрибутів кешуються в Redis (`search:facet-attributes`, усі локалі, TTL 10 хв; адмінка має викликати `SearchService.invalidateFacetCache()`), назви брендів — з `brands:list`. Чиста логіка — `search-filters.ts` і `search-facets.ts` (unit-тести). **`GET /api/v1/search/suggest?q=`** — автодоповнення: топ-товари (prefix search, `limit` ≤ 20, default 6) + до 5 категорій і 5 брендів зі збігом назви (ранг: початок назви → початок слова → підрядок, для складених слів «Електроточила»). Meilisearch недоступний або індексу нема → **503 `SERVICE_UNAVAILABLE`** (фільтр-помилки = баг → 500). Заміри на 46k: пошук з фасетами 13–32 мс (перший холодний ~290 мс), suggest ~50 мс. Фасети за `category_attributes.is_filterable` не обмежуються (показуються атрибути, що мають значення серед результатів).
- **Лістинги через пошук + деградація (7.4).** **Усі лістинги вітрини — `GET /api/v1/search`** (категорія = `?category=`, бренд = `?brand=`, `/sale` = `?sale=true`, `/antidron` = `?antidron=true`, пошук = `?q=`), SQL для фасетів/сортування не використовується. `GET /api/v1/products` лишається SQL-лістингом (найновіші; простий контракт) і водночас рушієм fallback: `ProductsService.listByFilter(locale, {categoryIds, brandIds, sale, antidron, inStock}, page, limit)`. **Meilisearch недоступний / повільний (> 2 с, `AbortSignal.timeout`) / індексу нема:** запит **без `q`** → SQL-fallback з `degraded: true` (враховуються категорія з піддеревом, бренди, sale/antidron, наявність — те саме правило, що InventoryService; ціна, атрибути, сортування й лічильники фасетів — ні; найновіші першими; вибрані значення лишаються у `facets` з count 0); запит **з `q`** → 503 `SERVICE_UNAVAILABLE`; `suggest` → `degraded: true`, товарів нема, категорії/бренди працюють. Інші помилки Meilisearch (напр. невалідний фільтр) = баг → 500. Перевірено зупинкою контейнера на 46k: fallback-лістинг ~190 мс, після старту Meilisearch усе повертається без дій (індекси на томі).

## Відкриті питання (потрібна відповідь замовника)
1. **Продаж зброї та патронів онлайн.** Законодавство України обмежує дистанційний продаж і доставку вогнепальної зброї та боєприпасів. Потрібен прапорець товару / категорії (напр. `saleMode: ONLINE | RESERVE_ONLY | INFO_ONLY`), щоб checkout дозволяв лише резерв чи самовивіз з перевіркою документів.
2. **Спосіб підключення Tria** (API / БД / файлообмін / local bridge) і правила синхронізації цін (§27).
3. **Платіжний провайдер** (LiqPay / WayForPay / Monobank / Fondy?) — у ТЗ не визначено.
4. **Доставка** (Нова Пошта / Укрпошта / Meest / самовивіз) — інтеграції не описані.
5. **Compute на AWS** для web/api/workers (ECS Fargate / App Runner / EC2) — §53 залишає відкритим.
6. **Email-провайдер** (SES / Postmark / інший).
7. **Error tracking** (Sentry?) та метрики — інструмент не вибрано (§48–49).
8. **Hreflang/URL-стратегія локалей**: префікс `/ru/`, `/en/` при `uk` без префікса?
9. Дубль у дереві: «ЗБРОЯ › Холодна зброя та інструменти › Ножі» vs «НОЖІ ТА ЛІХТАРІ › Ножі та комплектуючі» — товар може належати кільком категоріям (`product_categories`), але треба визначити основну (для canonical/breadcrumbs).
